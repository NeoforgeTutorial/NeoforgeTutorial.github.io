# 配方与战利品表

## 一、客户端资源与服务端数据

Minecraft 从资源包和数据包读取模组文件：

| 目录 | 加载位置 | 常见内容 |
| --- | --- | --- |
| `assets/<命名空间>/` | 客户端资源包 | 模型、贴图、语言、声音 |
| `data/<命名空间>/` | 数据包 | 配方、战利品表、标签、世界生成 |

`assets` 主要决定内容怎样显示，`data` 主要决定游戏规则。例如，物品模型放在 `assets`，但工作台能否用它合成另一件物品由配方决定，因此配方放在 `data`。

`data` 中的文件会由逻辑服务端加载。单人游戏也有内部服务端，所以配方和战利品表不会因为玩家在客户端而只存在于客户端。服务器加载数据后，客户端不会用本地 JSON 自行决定掉落或合成结果。

两类资源的完整目录列表见[资源](/docs/resources/)，客户端与服务端的职责划分见[逻辑客户端与服务端](/docs/concepts/sides/)。

文件路径中的命名空间通常就是 Mod ID。以银矿石为例：

```text
data/tutorialmod/recipe/silver_ingot_from_smelting_silver_ore.json
data/tutorialmod/loot_table/blocks/silver_ore.json
```

这些文件的路径和内容 ID 要互相配合。实际制作时，把 `tutorialmod`、`silver_ore`、`silver_ingot` 等示例名称替换为自己的命名空间、注册路径和文件名。

## 二、定义配方

配方描述某种制作行为接受哪些输入、应当输出什么。每个配方文件都有 `type`，它决定配方的输入和输出字段。常见配方类型如下：

| `type` | 用途 | 主要字段 |
| --- | --- | --- |
| `minecraft:crafting_shaped` | 有序工作台配方 | `key`、`pattern`、`result` |
| `minecraft:crafting_shapeless` | 无序工作台配方 | `ingredients`、`result` |
| `minecraft:smelting` | 熔炉 | `ingredient`、`result`、`cookingtime` |
| `minecraft:blasting` | 高炉 | `ingredient`、`result`、`cookingtime` |
| `minecraft:stonecutting` | 切石机 | `ingredient`、`result` |
| `minecraft:smithing_transform` | 锻造台转换 | `template`、`base`、`addition`、`result` |

这里只列出最常用类型和主要字段。各种类型的完整字段、可选配置和数据生成写法见[内置配方类型](/docs/resources/server/recipes/builtin/)。

如果原版类型无法表达所需行为，可以定义[自定义配方类型](/docs/resources/server/recipes/custom/)。配方文件也可以使用 `neoforge:conditions` 决定是否加载，见[数据加载条件](/docs/resources/server/conditions/)。

下面以把银矿石烧成银锭为例：

```json
{
  "type": "minecraft:smelting",
  "category": "misc",
  "cookingtime": 200,
  "experience": 0.1,
  "ingredient": "tutorialmod:silver_ore",
  "result": {
    "count": 1,
    "id": "tutorialmod:silver_ingot"
  }
}
```

`type` 选择熔炉配方。`ingredient` 是输入，直接填写物品 ID。假设已经创建标签 `tutorialmod:some_tag`，把输入写成 `#tutorialmod:some_tag` 时，就会接受标签中的任意物品。标签文件的位置、合并规则和命名方式见[标签](/docs/resources/server/tags/)。

原料并不只支持单个物品。多个物品、数据组件、组合原料和自定义原料见[原料](/docs/resources/server/recipes/ingredients/)。`result` 是结果物品堆，`count` 省略时为 1。

`cookingtime` 的单位是 tick，200 tick 等于 10 秒。`experience` 是每次完成配方获得的经验。`category` 只影响配方书中的分类，不决定配方在哪个方块中工作。

游戏不会按文件名判断配方内容，但文件名必须唯一。相同输入、相同结果也可以同时存在多个配方，例如分别添加熔炉和高炉版本：

```text
silver_ingot_from_smelting_silver_ore.json
silver_ingot_from_blasting_silver_ore.json
```

这两个配方需要不同的 `type`、`cookingtime` 和文件名，但可以使用相同的输入与结果。

如果多个配方同时匹配同一组输入，可以用[配方优先级](/docs/resources/server/recipes/#recipe-priorities)指定检查顺序。

工作台有序配方能更直观地说明 `key` 与 `pattern` 的关系。以银锭和木棍合成银镐为例（银镐需要单独注册）：

```json
{
  "type": "minecraft:crafting_shaped",
  "category": "equipment",
  "key": {
    "I": "tutorialmod:silver_ingot",
    "S": "minecraft:stick"
  },
  "pattern": [
    "III",
    " S ",
    " S "
  ],
  "result": {
    "id": "tutorialmod:silver_pickaxe"
  }
}
```

`I` 映射到银锭，`S` 映射到木棍；三行 `pattern` 分别表示银锭横排、中间放木棍、底部继续放木棍。空格表示空槽，每个字符都必须在 `key` 中有对应原料。

`pattern` 最多包含三行，每行最多三个字符。同一原料要在多个格子使用时，重复写同一个字符即可。

配方只在服务端检查。玩家放入原料后，`RecipeManager` 用当前容器类型和输入查找匹配配方，再组装结果。

配方 JSON 只定义输入、匹配条件和结果，不会自动生成配方书的解锁进度。手写 JSON 时，配方仍可正常合成，但它不会因为获得某种材料而自动在配方书中解锁；需要这项行为时，还要单独提供对应的进度文件。数据生成配方时，`.unlockedBy(...)` 会同时定义解锁条件并生成进度，因此不需要另外手写。

## 三、定义战利品表

以银矿石被正确工具破坏后掉落自身为例。方块默认使用 `data/tutorialmod/loot_table/blocks/silver_ore.json` 作为战利品表，文件内容为：

```json
{
  "type": "minecraft:block",
  "pools": [
    {
      "rolls": 1,
      "entries": [
        {
          "type": "minecraft:item",
          "name": "tutorialmod:silver_ore"
        }
      ]
    }
  ],
  "random_sequence": "tutorialmod:blocks/silver_ore"
}
```

最外层的 `"type": "minecraft:block"` 表示这是一张方块战利品表。`pools` 包含可以分别抽取的战利品组；本例只有一组，`rolls` 为 1，表示这组抽取一次。

`entries` 列出该组可能掉落的内容。内部条目的 `"type": "minecraft:item"` 表示掉落一个物品，`name` 则指向物品注册表中的 `tutorialmod:silver_ore`，也就是第 3 篇注册的 `BlockItem`。`random_sequence` 为随机抽取指定命名序列；即使当前每次都会得到同一个物品，也应提供一个属于这张表的固定标识。

战利品表可以进一步拆成以下层级：

| 层级 | 作用 |
| --- | --- |
| 战利品池 `pools` | 一组独立抽取机会 |
| 条目 `entries` | 池中可能被选中的结果及权重 |
| 函数 `functions` | 修改选中结果的数量、组件等 |
| 条件 `conditions` | 决定池或条目是否参与抽取 |

条目、函数和条件都不只有本文示例中的一种。完整列表见[战利品表](/docs/resources/server/loottables/)、[战利品函数](/docs/resources/server/loottables/lootfunctions/)和[战利品条件](/docs/resources/server/loottables/lootconditions/)。

一个池每次抽取时，会在 `entries` 中按权重选择一项。同一池有多个条目时，可以用 `weight` 调整被选中的概率。`rolls` 为 1 时抽取一次，也可以使用数值提供器生成随机次数；`bonus_rolls` 会结合幸运值增加抽取次数。

需要得到多组互相独立的结果时，通常使用多个池，而不是误以为同一池中的所有条目都会同时掉落。

条目不是只能写物品。条目还可以引用另一个战利品表、标签中的随机物品或空结果。函数在条目被选中后执行。例如，把前面的银矿石条目改成：

```json
{
  "type": "minecraft:item",
  "name": "tutorialmod:silver_ore",
  "functions": [
    {
      "function": "minecraft:set_count",
      "count": {
        "type": "minecraft:uniform",
        "min": 1,
        "max": 3
      }
    }
  ]
}
```

原来的条目只会掉落一个银矿石。加入 `set_count` 后，条目仍由同一个池抽取，但每次选中它会生成一个数量随机的银矿石物品堆，最终得到 1 到 3 个银矿石。

这个函数只修改被选中结果的数量，不会增加抽取次数，也不会改变条目被选中的概率。`rolls: 1` 仍表示池抽取一次；如果 `rolls` 为 2，就会分别抽取两次，并对每次选中的结果执行函数。

函数也可以单独写成下面的对象，再放入条目或战利品池的 `functions` 列表：

```json
{
  "function": "minecraft:set_count",
  "count": {
    "type": "minecraft:uniform",
    "min": 1,
    "max": 3
  }
}
```

多个函数按列表顺序执行，所以数量、名称或数据组件的修改顺序会直接影响最终结果。

条件与函数不同。例如，条件可以只在工具带有精准采集时启用某个条目，或只在爆炸没有摧毁掉落物时继续。条件失败时，该池或条目不会产出。

方块、实体、箱子、钓鱼等对象使用不同的战利品上下文。方块默认查找 `<命名空间>:blocks/<注册路径>`，实体默认查找 `<命名空间>:entities/<注册路径>`。文件最外层的 `type` 负责声明这张表要求哪类上下文；把方块战利品表拿给实体使用，字段和可用参数通常会不匹配。

战利品表不是“任何情况下都会执行”。第 3 篇中的 `requiresCorrectToolForDrops()` 和工具标签仍会先决定方块是否允许产生掉落。允许产生掉落之后，游戏才从战利品表中抽取具体结果。因此，方块没有掉落时，应分别检查工具条件、方块标签和战利品表。

通常只为自己注册的方块或实体建立战利品表。若要给原版或其他模组的现有战利品表增加掉落，应使用[全局战利品修改器](/docs/resources/server/loottables/glm/)，而不是复制并覆盖原表；否则其他数据包所做的修改也会被你覆盖。

战利品表根对象还能使用 `neoforge:conditions`。它与池里的普通 `conditions` 不同：根条件决定整个文件是否加载，文件加载失败时，战利品表通常会被当成空表。数据加载条件的完整写法见[数据加载条件](/docs/resources/server/conditions/)。

配方和战利品表都可以继续以手写 JSON 的方式维护；下一篇会把这两类文件改为数据生成。
